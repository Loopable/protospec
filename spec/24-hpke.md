# 24. HPKE

This module is the authoritative definition of HPKE usage for wrapping object content-encryption keys. It defines the recipient key descriptor, the recipient key identifier, the HPKE `info` construction, and the recipient key record. The construction is deliberately acyclic: every input to HPKE is computable before encryption.

## 24.1 Purpose

HPKE delivers a per-object content-encryption key (CEK) to one recipient. For each device recipient of an object, the sender encapsulates the CEK with the recipient's X25519 public key. Instances store the encapsulated ciphertext and never require the CEK.

## 24.2 Suite

The mandatory Loopable HPKE suite, per `20.8`:

| Component | Value | ID |
| --------- | ----- | -- |
| KEM | DHKEM(X25519, HKDF-SHA256) | 0x0020 |
| KDF | HKDF-SHA256 | 0x0001 |
| AEAD | AES-256-GCM | 0x0002 |

The HPKE Base mode MUST be used for all objects defined by this specification.

## 24.3 Encryption of an object key

To wrap the CEK for one device recipient, an implementation MUST:

1. Obtain the recipient device's X25519 public key `pkR`.
2. Compute the recipient key descriptor and `recipient_key_id` per `24.4`.
3. Compute `info` per `24.5`.
4. Compute `(enc, ct) = HPKE.SealBase(pkR, info, aad, CEK)` with `aad` being the empty byte string.
5. Produce the recipient key record per `24.6` containing `recipient_key_id`, `enc`, and `ct`.

Each recipient MUST receive independently protected key material. The same CEK MAY be wrapped for multiple recipients. The plaintext CEK MUST NOT be sent directly to recipients over federation.

## 24.4 Recipient key descriptor and recipient_key_id

A `recipient_key_id` identifies a recipient public key. It MUST be computable before any HPKE operation, and MUST NOT depend on the HPKE output, the encapsulated key, the wrapped key, the ciphertext, the complete recipient record, or any value produced by encryption.

For a device recipient (`recipient_kind = 0`), the recipient key descriptor is the canonical CBOR map:

| Key | Field | Type | Description |
| --- | ----- | ---- | ----------- |
| 0 | `recipient_kind` | uint | `0` for a device recipient. |
| 1 | `account_id` | bytes(32) | The recipient account. |
| 2 | `device_id` | bytes(16) | The recipient device. |
| 3 | `recipient_public_key` | bytes(32) | The recipient device's X25519 public key. |

The recipient key identifier is:

```text
recipient_key_id = first 16 bytes of SHA-256(
    "loopable-recipient-key-id-v1" 0x00 ||
    deterministic_cbor(recipient_key_descriptor))
```

The descriptor contains exactly the information needed to identify the recipient key under the Loopable key model. The descriptor MUST NOT contain ciphertext-dependent fields, and the encoding MUST follow `30-serialization.md`.

For an MLS group recipient (`recipient_kind = 1`), no HPKE is performed and `recipient_key_id` is the first 16 bytes of the MLS `group_id`, per `25.6`.

The identifier is stable for a given recipient public key: the same device key produces the same `recipient_key_id` across objects. There is no envelope-level key identifier; the envelope identifier is a separate, derived value defined in `33-object-envelope.md` and is never an input to HPKE.

## 24.5 HPKE info

The `info` parameter is domain-separated and constructed as:

```text
info = "loopable-hpke-object-key-v1" 0x00 ||
       object_id            (32 raw bytes) ||
       recipient_key_id     (16 raw bytes) ||
       utf8("0.1")          (the protocol version text, raw bytes)
```

The exact bytes follow `20.12`. Every component of `info` is known before encryption: `object_id` is generated by the sender, and `recipient_key_id` is computed per `24.4`. `info` MUST NOT depend on the encapsulated key, the wrapped key, the ciphertext, or any envelope identifier derived from them.

## 24.6 Recipient key record

A recipient key record is the CBOR map:

| Key | Field | Type | Description |
| --- | ----- | ---- | ----------- |
| 0 | `recipient_kind` | uint | `0` device, `1` MLS group. |
| 1 | `account_id` | bytes(32) | The recipient account (empty for MLS group records). |
| 2 | `device_id` | bytes(16) | The recipient device (empty for MLS group records). |
| 3 | `recipient_key_id` | bytes(16) | The recipient key identifier, per `24.4`. |
| 4 | `encapsulated_key` | bytes | The HPKE encapsulated key `enc`. |
| 5 | `wrapped_key` | bytes | The HPKE ciphertext `ct` containing the CEK. |

For `recipient_kind = 0` (device), fields 1, 2, 3, 4, and 5 MUST be present; fields 1, 2, and 3 MUST be non-empty. For `recipient_kind = 1` (MLS group), the record is defined by `25.6`.

An unauthorized recipient MUST NOT receive usable key material. A recipient that matches neither an HPKE record nor the MLS group MUST treat the object as undecryptable and MUST NOT treat that as a protocol error.

## 24.7 Recovery of the object key

To recover the CEK, a device MUST:

1. Recompute its own recipient key descriptor and `recipient_key_id` per `24.4`.
2. Select the recipient record with `recipient_kind = 0` whose `account_id` and `device_id` match its own and whose `recipient_key_id` matches the recomputed value.
3. Compute `info` per `24.5` using the envelope's `object_id` and the record's `recipient_key_id`.
4. Compute `CEK = HPKE.OpenBase(pkR=own_public_key, skR=own_private_key, info, aad, enc, ct)` with the empty `aad`.
5. Use the recovered `CEK` to authenticate and decrypt the object per `23.5`.

An HPKE authentication failure MUST be treated as a failed decryption with error code `E_DECRYPTION_FAILED` (`80-errors.md`). A recipient MUST NOT attempt alternative keys indefinitely.

## 24.8 Construction order

The construction is acyclic and MUST be performed in this order:

```text
recipient public-key descriptor
        |
        v
recipient_key_id                    (24.4)
        |
        v
HPKE info                           (24.5)
        |
        v
HPKE encryption                     (24.3)
        |
        v
encapsulated_key / wrapped_key
        |
        v
recipient record                    (24.6)
        |
        v
complete object envelope            (33)
        |
        v
envelope_id                         (33.3, derived after the envelope is complete)
```

No step may depend on a later step. In particular, `recipient_key_id` MUST NOT be computed from `encapsulated_key`, `wrapped_key`, `ciphertext`, or the complete recipient record, and the HPKE `info` MUST NOT include `envelope_id`.

## 24.9 Revocation

Removing a recipient from future access does not retroactively make previously obtained plaintext disappear. For future objects, the sender MUST exclude the revoked recipient from new key envelopes. For groups, MLS membership changes MUST be used, per `25-mls.md`. If stronger cryptographic revocation of existing ciphertext is required, the protocol MUST rotate the relevant encryption key and create a new encrypted version, per `55-content.md`.
