# 0014: Object version_id is required in protocol version 0.1

* Status: accepted
* Basis: `spec/23-encryption.md` 23.4, `spec/33-object-envelope.md` 33.2 and 33.4, `spec/55-content.md` 55.3

## Context

`decisions/0013` bound `version_id` into the object AES-GCM associated data. It left the field marked optional and said it was present "exactly when the object envelope carries a `version_id`". The specification never said which object types are versioned, so the encryption side had no deterministic rule for whether to include the field. Two conforming encryptors of the same logical object could therefore produce different `ObjectSecurityMetadata` bytes, different AAD, different ciphertext, and mutually undecryptable objects.

## Alternatives

1. Keep `version_id` optional and list which of the ten object types of `33.7` are versioned. Rejected: it requires designating versioned status for types the specification does not describe as mutable, and the registry would need to stay authoritative for every future type.
2. Always require `version_id` in protocol version 0.1. Chosen.
3. Leave the ambiguity and record it as blocking. Rejected: the value is already generated by the encryptor, so requiring it costs nothing and removes the ambiguity outright.

## Decision

In protocol version 0.1 every object has a version identity, so the object envelope MUST carry `version_id` (key 4), and the AES-GCM associated data MUST include it. `spec/33-object-envelope.md` 33.2 marks the field required, `spec/23-encryption.md` 23.4 always includes key 4, and `spec/55-content.md` 55.3 states that every object has at least one version. This narrows `decisions/0013`, which remains the AAD definition.

## Consequences

* Encryptors have one deterministic rule: `version_id` is always present.
* Object types with a single version, such as `mls_message`, still carry a `version_id`; it is a random value that is never incremented.
* `decisions/0013`'s "present exactly when the envelope carries it" wording is superseded by this decision; the envelope always carries it in version 0.1.
* Event-level `object_reference.version_id` (`spec/32-event-envelope.md` 32.2) is not changed by this decision.
